## Подключение

`App.vue` формирует снимок через существующий `toSearchRequest()`. `useReferenceSearch` проверяет базовую структуру и вызывает адаптер `api/references.ts`, который использует сгенерированный `ReferencesApi.searchReferences({ searchRequest }, { signal })`. Запрос: `POST /api/v1/references/search`. DTO импортируются из `api/generated`; контракт — `backend/openapi.yaml`.

`SearchRequest` содержит всех людей, явные связи и выбранные `personA` / `personB`. Координаты и локальные ID связей исключены. Пустые связи допустимы. Проверяются наличие двух разных выбранных людей, уникальность и непустота ID, ссылки и типы связей. Семантическая проверка, извлечение и кодирование путей, `contains` и вердикты остаются на backend.

### Конфигурация

Из корня проекта, в отдельном терминале:

```sh
cd backend
./gradlew bootRun
```

В другом терминале:

```sh
cd frontend
# Выберите версию проекта (при установленном nvm):
nvm use
npm ci
npm run dev
```

Переменные описаны в `frontend/.env.example`. Можно скопировать его в `.env.local`:

- `VITE_API_BASE_URL` — публичный origin API **без `/api` в конце**. По умолчанию пустой: запросы идут на текущий origin. Vite подставляет значение при запуске/сборке; после изменения нужен перезапуск или пересборка.
- `API_PROXY_TARGET` — адрес Spring Boot для dev proxy `/api`, по умолчанию `http://127.0.0.1:8080`. Путь сохраняется, префикс не удаляется. Значение не передаётся браузеру.

В production нужен reverse proxy `/api` либо `VITE_API_BASE_URL` и разрешённый сервером CORS. `vite preview` не заменяет production reverse proxy.

## Работа с интерфейсом

«Участники и результаты» открывает панель выбора A/B без запроса. Можно выбрать любых двух разных людей графа. Их роли на холсте обновляются; выбранные участники защищены от удаления. «Найти совпадения» отправляет текущий граф и открывает результаты. «Повторить поиск» отправляет новый запрос из панели результатов. Панель закрывается кнопкой × или Escape; действия конструктора сохраняются. На мобильном она открывается как нижняя модальная панель с прокруткой.

Состояния: начальное, загрузка, успешный ответ, пустой ответ, ошибка. Во время загрузки повторная отправка блокируется. Сетевые ошибки, HTTP 400 и серверные ошибки имеют понятные сообщения; технические ответы сервера не выводятся.

Совпадения группируются по возвращённому вердикту: красный `FORBIDDEN`, жёлтый `UNDETERMINED`, зелёный `ALLOWED`. Внутри групп сохраняются все записи, включая одинаковые ID/коды, соответствующие разным путям. При одновременных `FORBIDDEN` и `ALLOWED` выводится пояснение о противоречии. Общий вердикт не вычисляется. Пустой ответ не считается разрешением.

Карточка показывает `referenceId`, вердикт, описание, `userPathCode`, `referencePathCode` и известные поля `source`: документ, страницу, пример и заключение. Отсутствующие сведения не выдумываются. API не возвращает последовательность ID людей конкретного пути, поэтому выделение совпавших рёбер на холсте не реализовано.

Любое изменение сериализуемого графа (включая имена), A или B немедленно очищает результаты и отменяет запрос через `AbortController`. Счётчик ревизии дополнительно игнорирует поздний ответ или ошибку, даже если отмена не остановила транспорт. При повторном поиске старые карточки очищаются до ответа. Перетаскивание узлов и выбор карточки для редактирования не изменяют запрос и не сбрасывают результаты.

## Три ручных сценария по реальному каталогу

Ожидания ниже проверены на текущем `backend/src/main/resources/references.json` и действующем `PathMatcher`. Это не синтетические mock-ответы.

| Сценарий | Построение | Реальный ответ |
| --- | --- | --- |
| A: `<BB>` | Добавить родителя к A; связать его с B в роли ребёнка | 5 записей `FORBIDDEN`: `blood-01`, `blood-02`, `blood-03`, `blood-04`, `blood-05`. У всех `userPathCode = <BB>` |
| B: `<BMB>` | Добавить отдельного родителя к A и отдельного к B; соединить родителей браком; выбранными оставить исходные A/B | `matches: []`. В текущем каталоге нет подходящего случая для этого пути по действующим правилам |
| C: нет пути | После сброса оставить двух несвязанных A/B | `matches: []`; интерфейс сообщает, что это не означает разрешения |

В A возвращается не только `blood-01`: для `FORBIDDEN` backend проверяет, содержит ли справочный код пользовательский либо его обратный код. Справочные коды: `<BB>`, `<BB>B>`, `<BB>B>B>`, `<B<BB>B>`, `<BB>B>B>B>`. Для `ALLOWED` направление проверки `contains` обратное: пользовательский код должен содержать справочный. Frontend эти правила не повторяет.

Готовые JSON-запросы: [A](examples/day9/common-parent.json), [B](examples/day9/parents-marriage.json), [C](examples/day9/disconnected.json). Например, из корня проекта при работающих Vite и backend:

```sh
curl -H 'Content-Type: application/json' \
  --data-binary @docs/examples/day9/common-parent.json \
  http://127.0.0.1:5173/api/v1/references/search
```

## Автоматические проверки

В `frontend`:

```sh
npm run build
npm test
npm run test:e2e
```

Unit-тесты выполняют сгенерированный клиент с mock `fetch`: тело запроса, выбор A/B, состояния, HTTP/сеть, валидация, очистка результатов, двойной запрос, поздние успешные ответы и ошибки, отмена при закрытии компонента. Браузерные mock-тесты проверяют все цвета и вердикты, противоречащие случаи, nullable-поля, источники/коды, пустое состояние, ошибки, изменение графа и A/B, повторную отправку и адаптивность. Ранее существовавшие сценарии редактора выполняются вместе с ними.

Для реальных сквозных браузерных тестов сначала запустите backend. Затем в `frontend`:

```sh
RUN_BACKEND_INTEGRATION=1 API_PROXY_TARGET=http://127.0.0.1:8080 \
  npm run test:e2e -- backend.spec.ts
```

Эти три теста проходят цепочку UI → generated client → Vite proxy → Spring Boot → реальный каталог без mock API. Без переменной они явно пропускаются. Тестовый Vite использует порт 4173.

В `backend`:

```sh
./gradlew test --rerun-tasks openApiValidate
```

История локальной проверки Дня 9 (2026-11-08), подтверждённая журналами соответствующих запусков: сборка TypeScript/Vite успешна, 44 unit-теста, 24 обычных браузерных сценария, 3 реальных сквозных сценария и 216 backend-тестов прошли; OpenAPI validation успешна. Эти результаты относятся к проверенному тогда состоянию проекта и перечисленным наборам, а не ко всем возможным проверкам или последующим изменениям. При текущем обновлении документации тесты повторно не запускались.

Генерация клиента выполняется перед сборкой/тестами. В рамках проверки Дня 9 все три JSON-запроса также отправлены через отдельный Vite proxy (5419 → 18080); исходники backend, контракт и каталог были сохранены побайтово.

Скриншоты создаются в `frontend/artifacts/`: `search-mixed-1440.png`, `search-mixed-390.png` (mock всех вердиктов), `search-real-bb.png`, `search-real-bmb-empty-mobile.png` (реальный backend). Каталог артефактов исключён из Git.

## Границы работы

Черновик хранится в памяти вкладки. Авторизация, сохранение графа и выделение путей на холсте не реализованы. Техническая часть Дня 10 (Docker, развёртывание и smoke-тест frontend/API) завершена; публичный релиз зависит от доступности IP хостинга из российских сетей. Результаты описывают конкретные справочные случаи; окончательное заключение frontend не делает. Обработка избыточных `<BMB>` во frontend не добавлялась; существующее поведение backend оставлено без изменений. Проверка уже реализованных механизмов и дальнейшие улучшения распределены по [этапам roadmap](roadmap.md).
