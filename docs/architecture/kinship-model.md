# Relationer — семейные группы и кодирование родства

**Статус:** согласованное архитектурное решение. Фильтрация избыточных путей реализована в поиске и покрыта регрессионными тестами. Раздел о семейных связях в UX описывает текущую модель конструктора.

## 1. Основной принцип

**Каждый узел конструктора представляет отдельного человека. Семья задаётся связями между людьми, а не отдельной группой или типом родства.**

Наличие брака между родителями не означает, что переход `M` должен присутствовать в коде кровного родства их детей.

Следует различать:

- `BIOLOGICAL` — биологическую связь «родитель → ребёнок», образующую кровное родство;
- `MARRIAGE` — супружескую связь;
- родство по свойству — путь, проходящий через супружескую связь между разными семейными ветвями.

В [предметных правилах](../kinship-rules.md) `BLOOD` обозначает вид родства; `BIOLOGICAL` здесь обозначает тип связи графа и публичного API.

## 2. Кровное родство: `<BB>`

Если у двух людей есть общий биологический родитель, их кровное родство выражается путём:

`A → общий родитель → B`

Код: `<BB>` (переход к родителю `<B`, затем к ребёнку `B>`).

Это справедливо независимо от:

- наличия брака между родителями;
- наличия второго известного родителя;
- того, являются ли дети полнородными или неполнородными братьями и сёстрами.

Если известны два общих родителя, граф может содержать два различных пути с кодом `<BB>`. Они различаются участниками, даже если их коды совпадают.

Брак родителей не добавляет `M` в этот код.

## 3. Родство по свойству: `<BMB>`

Если у A и B разные биологические родители, состоящие в браке, путь имеет вид:

`A → родитель A → родитель B (супруг родителя A) → B`

Код: `<BMB>` (переход к родителю `<B`, к его супругу `M`, затем к ребёнку супруга `B>`).

Такой путь представляет родство по свойству, а не кровное родство. Пример: дети супругов от предыдущих браков, не имеющие общего биологического родителя.

`<BB>` и `<BMB>` не являются взаимозаменяемыми кодами.

## 4. Избыточные пути

В графе с двумя общими родителями, состоящими в браке, технически могут существовать как пути `<BB>`, так и пути `<BMB>`.

**Принятое семантическое правило:** путь через брак общих родителей не должен создавать самостоятельное совпадение по свойству между детьми, кровное родство которых уже установлено.

Это правило не означает глобального запрета на пути с `M` при наличии любого кровного пути. Оно относится к конкретному обходу через супругов-родителей. Другие содержательные пути по свойству должны сохраняться.

`PathExtractor.extract` сохраняет все простые пути. `extractForSearch` исключает пути с фрагментом `ребёнок A → родитель A → супруг (родитель B) → ребёнок B`, только если оба родителя являются биологическими родителями обоих детей. Фрагмент проверяется и внутри более длинного пути. Наличие отдельного кровного пути само по себе не исключает пути по свойству.

`ReferenceSearch` использует `extractForSearch` для пользовательского графа и справочных графов. Исходные люди и связи не изменяются; правила `PathMatcher` и справочные примеры сохраняются.

## 5. Семейные связи в UX

Конструктор использует обычных людей и явные связи. Пользователь может добавить одного общего родителя или двух отдельных родителей, связать каждого с существующими детьми, добавить брак и детей от разных союзов. Один общий родитель достаточен для представления кровного пути `<BB>`.

Специального узла «Родители», локального признака группы и сериализации в техническую персону нет. Каждый узел соответствует одной персоне в `SearchRequest`. Все семь ролей родственников доступны для любого человека.

Родительские связи создаются через `BIOLOGICAL`, брак — только явным действием через `MARRIAGE`. Неизвестные родители автоматически не создаются; брак не означает общего родительства.

Раскрывающаяся подсказка «Как добавить родителей» объясняет минимальный и подробный ввод дерева, а также различие `<BB>` и `<BMB>`. Конструктор не вычисляет эти коды и не фильтрует пути; семантика поиска из раздела 4 сохраняется.

Порядок действий описан в [документации конструктора](../family-groups.md).

## 6. Реализованная совместимость

Токены `B>`, `<B`, `M` и асимметричные правила `PathMatcher` используются
в текущем поиске. Типа `FAMILY` в API нет. Фильтрация не меняет исходный
граф, даже если некоторые пути исключаются из поискового представления.
Общая структура, категории и read API описаны в [архитектуре](overview.md).

## 7. Регрессионные проверки

Покрытые регрессионными тестами сценарии:

1. Общий родитель → `<BB>`.
2. Два общих родителя → два пути `<BB>` через разных родителей.
3. Разные родители, состоящие в браке → `<BMB>`.
4. Общие родители в браке → кровные пути сохраняются, избыточные обходы через `M` исключаются из поиска; исходные связи графа сохраняются.
5. Один известный родитель → кровный путь работает без второго родителя и без создания фиктивной персоны.
6. Повторные браки и дети от разных союзов → родство по свойству не теряется, в том числе при наличии отдельного кровного пути.

Сценарии проверяются в `FamilyPathsTest`, включая оба направления поиска, фрагмент внутри длинного пути и фильтрацию пользовательских и справочных путей.

## 8. Источник

«О брачном праве. Сборник статей о различных видах родства» (1900), стр. 49 — указана для проверки примера родства по свойству.

Точное соответствие примера на странице 49 данному правилу требует сверки с оригиналом. Ссылка фиксируется как ориентир для будущей проверки, а не как подтверждение правила по первоисточнику.
