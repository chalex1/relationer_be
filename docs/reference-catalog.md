# Единый каталог Relationer (MVP)

Состояние: 11 ноября 2026. Каталог хранится в backend и читается через существующий
REST API. Архив `relationer-full-catalog-stage17.zip` импортирован: 94 черновых
кейса и 94 PNG. Все импортированные графы имеют `reviewStatus: DRAFT`.

## Хранение и совместимость

```text
backend/src/main/resources/reference-catalog/
    references.json         # 11 прежних рабочих записей
    references-draft.json   # 94 записи накопительного архива
    images/                 # 94 оригинальных PNG
```

Из frontend/public изображения удалены. Frontend не содержит копий данных
runtime-каталога, получает метаданные, графы и PNG через API. В тестах используются
backend-ресурсы. Каталог и изображения входят в bootJar; внешнее хранилище и БД
не нужны. После изменения JSON/PNG требуется пересборка и перезапуск backend.

PNG не хранятся в Git: папка `reference-catalog/images/` исключена через
`.gitignore`. После клонирования скопируйте её из локального архива каталога
или подготовленной рабочей копии в указанный путь до сборки и запуска тестов
изображений. При сборке локальные PNG по-прежнему включаются в bootJar.

Архив накопительный: в 94 черновика входят те же 11 рабочих ID с теми же данными.
Оба JSON сохранены отдельно. Чтение по ID и поиск используют объединение по ID,
с приоритетом рабочей записи. Повторные записи допустимы только при совпадении
метаданных, источников, участников и графов; расхождение останавливает загрузку,
чтобы не выбирать версию молча. Сейчас в поиске 94 уникальных кейса, а не 105.
Поле API `catalog` показывает приоритетный каталог: production для общих ID,
draft для остальных. `catalog=draft` при этом возвращает все 94 архивные записи.

`ReferencePattern`, `Verdict`, PathExtractor, PathEncoder, PathMatcher и алгоритм
ReferenceSearch сохранены. Обёртка `ReferenceCatalogEntry` добавляет title,
reviewStatus и sources. Загрузчик читает новый формат и старый source/verdict
для fixtures и прежних файлов. В архиве 8 связей `ADOPTED`: загрузчик принимает
это как синоним существующего ADOPTION. Исходные строки связей в JSON сохранены;
API выдаёт нормализованный ADOPTION. Направление усыновитель → усыновлённый неизменно.

### Уточнения каталога и раскладки, 13 ноября 2026

Категории отражают вид родства выбранной пары: наличие вспомогательных
биологических связей в схеме свойства или духовного родства само по себе
не добавляет BLOOD. Поэтому BLOOD удалён из таких записей в обоих JSON;
составные категории SPIRITUAL/AFFINITY и ADOPTION/AFFINITY сохранены.
Семь случаев с двумя браками отмечены тегом «трехродное свойство».
В заголовках и описаниях `affinity-forbidden-20` и `affinity-forbidden-27`
уточнены степени на 7-ю и 5-ю соответственно. Это текущие редакционные
правки; предметная сверка первоисточников остаётся открытой.

Раскладка выравнивает поколения обеих семей относительно брака, сохраняет
короткие ветви на соответствующих уровнях и размещает потомков под их
родителями внутри супружеской группы. Восприемник размещается рядом с
родителем крестника, если это не объединяет предка с потомком. При конфликте
расстояний между поколениями используется порядок родителей перед детьми;
для циклов сохраняется fallback Dagre. Исходные люди, A/B и связи не меняются.

Unit-проверка охватывает все 94 графа. Браузерные регрессии проверяют
вмещение и отсутствие пересечения линиями посторонних карточек на desktop
и при ширине 390 px для выбранных сложных схем; снимки сохраняются в
`frontend/artifacts/layout/`. Тестовые данные нормализуют ADOPTED в ADOPTION,
как реальный API.

Проверка этой итерации: 244 backend-теста и `openApiValidate`, 78 frontend
unit-тестов, TypeScript и production-сборка прошли. Playwright с
`RUN_BACKEND_INTEGRATION=1` — 61 тест прошёл, без пропусков. Изображения в
изолированных браузерных тестах выдаются из backend-ресурсов через mock;
интеграционные сценарии используют настоящий локальный backend.

## Формат

У кейса сохраняются id, persons, relations, personA, personB, categories, tags,
description. Добавлены краткий title, reviewStatus и непустой список sources.
Краткие названия получены из существующих описаний до двоеточия; они могут
уточняться человеком. Описания, A/B, связи и исторические выводы не исправлялись.

Пример структуры источника (значения берутся из конкретного первоисточника):

```json
{
  "id": "source-1900",
  "title": "Название документа",
  "page": 111,
  "verdict": "FORBIDDEN",
  "conclusion": "Вывод источника",
  "example": "Изображение 1",
  "image": "images/case-id.png"
}
```

ID источника уникален внутри кейса. Page положительная, поля example, conclusion
и image необязательны. В PNG сохраняются все узлы, линии, подписи и номер схемы.
Путь image относителен reference-catalog; выдаются только PNG из images/ с именами
из латинских букв, цифр, точек, дефисов и подчёркиваний. Клиент не передаёт путь файла.

У каждого импортированного кейса один источник, перенесённый из source без изменения
страницы, описания документа и вердикта. Старые source/verdict не дублируются в новом
JSON. В API они остаются совместимыми алиасами первого источника. Все sources
возвращаются отдельно; интерфейс показывает каждый вывод и позволяет выбрать
оригинальную схему, если источников несколько.

## Граф и вывод источника

- DRAFT — граф ещё не проверен.
- REVIEWED — человек проверил соответствие графа оригиналу.
- NEEDS_CORRECTION — найдена ошибка графа.

Ни REVIEWED, ни нахождение совпадения не подтверждают достоверность исторического
вердикта. FORBIDDEN/ALLOWED/UNDETERMINED принадлежат источнику. Автоматического
заключения приложения, рейтинга источников и разрешения противоречий нет.

Существующий PathMatcher использует Verdict для выбора направления contains.
Для совместимости в ReferencePattern проецируется первый источник, включая его
вердикт. Это техническое правило прежнего поиска, а не подтверждение вывода.
Добавление второго источника не агрегирует выводы и не меняет это правило;
перестановка первого источника может изменить поиск и требует предметного решения.

## REST API

Используется существующий префикс `/api/v1`, без параллельного `/api/references`.

| Операция | Поведение |
| --- | --- |
| GET /api/v1/references | Метаданные объединения без повторов ID |
| GET /api/v1/references?catalog=production | 11 рабочих записей |
| GET /api/v1/references?catalog=draft | 94 записи чернового файла |
| GET /api/v1/references/{id} | Метаданные и полный граф из того же каталога |
| GET /api/v1/references/{id}/image | PNG первого источника |
| GET /api/v1/references/{id}/image?sourceId=... | PNG выбранного источника |
| POST /api/v1/references/search | Прежний алгоритм, 94 уникальных кейса обоих каталогов |

Список принимает category (BLOOD/AFFINITY/SPIRITUAL/ADOPTION), reviewStatus,
search и sort. Search ищет без учёта регистра по ID, title, description, tags и
названию/примеру/выводу каждого источника. Фильтры сочетаются по И.
Sort: id, title, page, -id, -title, -page; без sort сохраняется порядок файлов.
При сортировке по page используется первый источник; неизвестная страница имеет
максимальное значение. Неизвестные значения фильтров дают 400, неизвестный ID,
источник или отсутствующий PNG — 404. Маршрут /drafts заменён параметром catalog;
изображение имеет отдельный конкретный маршрут и не принимается за ID кейса.

Image URL формируется backend; параметр v содержит SHA-256 байтов PNG. Изменение
оригинала меняет URL и отпечаток ревью даже при сохранении имени файла.
Источник, title, graph reviewStatus и принадлежность к каталогу возвращаются
также с поисковым совпадением. Общий вердикт приложения не вычисляется.

Если черновой JSON отсутствует или не проходит валидацию, приложение сохраняет
рабочий каталог: запрос списка черновиков/объединения возвращает 503, поиск
работает по production и возвращает catalogWarning. UI явно показывает предупреждение.
Ошибка рабочего каталога по-прежнему препятствует старту. При исправлении ресурсов
необходим перезапуск. API записи JSON отсутствует.

## Работа с ревью

1. Добавьте/измените references-draft.json в указанном каталоге. В новом кейсе
   задайте уникальный ID, человеческие title/description, исходные связи и A/B,
   категории/теги, sources и reviewStatus=DRAFT. Изображение поместите в images/.
   Повтор рабочего ID разрешён только для идентичной записи. Пересоберите backend.
2. Откройте `/references`, выберите «На проверке». Рабочие и черновые кейсы
   используют те же ReferenceCard/ReferenceGraph и компактный layout. Есть поиск,
   сортировка, категории, теги, фильтр по статусу графа, счётчики, порции карточек
   по 10 и infinite scroll. На desktop граф и PNG рядом, на mobile вертикально.
3. Сверьте PDF-страницу и печатную страницу, номер схемы, всех людей, каждую связь
   и её направление, выбранные A/B. Проверяйте текст вокруг схемы отдельно от графа.
   В интерфейсе отметьте REVIEWED или NEEDS_CORRECTION; для ошибки можно оставить
   комментарий. Эти отметки локальны, не меняют JSON, Verdict и участие в поиске.
4. Скачайте «Экспорт результатов»: review-results.json содержит version=1 и results
   с id, fingerprint, status, comment, reviewedAt (ISO UTC; для непроверенного кейса null).
   «Импорт результатов» проверяет файл целиком и объединяет отметки по ID. Невалидный
   файл ничего не перезаписывает. Совпавший ID с другим содержимым не получает старое
   одобрение: эффективный статус DRAFT и сообщение о повторной проверке.
5. Для фиксации результата в репозитории человек отдельно проверяет экспорт и
   редактирует серверный reviewStatus. Перенос в production выполняется вручную,
   независимо от вердикта источника; интерфейс ничего не публикует.

Отметки хранятся в localStorage под relationer.reference-reviews.v1, без
авторизации и синхронизации между устройствами. При недоступном storage остаются
до закрытия страницы и могут быть экспортированы. Fingerprint sha256-v2 считается
по каноническому содержимому DTO, включая граф, источники и версии изображений;
порядок людей/связей/множеств не влияет. Старые PENDING/APPROVED/REJECTED при импорте
читаются как DRAFT/REVIEWED/NEEDS_CORRECTION, но старый fingerprint v1 требует
повторной проверки. Для Web Crypto нужен localhost или HTTPS.

## Проверки

Backend: `./gradlew test openApiValidate bootJar`. Frontend: `npm test`,
`npm run build`, `RUN_BACKEND_INTEGRATION=1 npm run test:e2e -- --workers=2`.
Для последней команды нужен запущенный backend; API_PROXY_TARGET позволяет
направить Vite на отдельный порт проверяемого JAR.

Сохранение исходных данных, количество PNG и окончательные результаты —
в [отчёте импорта](reference-catalog-import-stage17.md). День 12 остаётся открытым.
